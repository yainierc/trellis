Quickstart

Two commands to install, then one sentence per thing you want. Claude Code does the setup — it can read your repo and run your build, which is more than a page of instructions can do.

1 Install the plugin

This part is yours — the plugin has to exist before an agent can use it. No build, no installer; a plugin is distributed as source. The only prerequisite is Node on your PATH. 

claude plugin marketplace add yainierc/trellis
claude plugin install trellis@gmstek

Restart your session, or run /reload-plugins.

2 Ask Claude Code to adopt it

Open a session in the repository you want under Trellis and say it. Nothing else.

You say Adopt trellis in this project
No code yet? Start here anyway

A folder holding requirement PDFs and Word documents is a repository Trellis can govern, and git is not required — the write boundary, the Stop gate and the validator all work without one. Say "write a spec from these documents" and /trellis:spec reads them and produces a spec that keeps what the source decided, what it assumed on your behalf, and what is missing strictly apart. That separation is the point: an assumption written in as a requirement is what nobody catches until it is expensive.

That runs /trellis:init. What it does, and why it is better than you doing it by hand:

  • Reads the repo to find the stack — your package.json scripts, your .sln, your Bicep files — instead of assuming.
  • Runs every candidate command and watches whether it works before writing it into the profile. It tells the difference between "that command does not exist" and "your repo is red right now". Only the first disqualifies a command.
  • Writes .trellis/profile.yml, marking anything this repo does not have as ~ — a real answer, not a blank.
  • Creates the directories for specs, contracts and decisions, and gitignores the scratch path.
  • Tells you enforcement is still silent, and what turns it on.
Why verifying matters

A profile holding a plausible command that does not exist is the one setup mistake that makes Trellis untrustworthy: the Stop gate runs those commands every time a session closes, so a wrong one marks perfectly good work blocked and sends you debugging code that is fine. Running them once at setup removes the whole failure class.

It will ask before overwriting a profile you already tuned, and it will ask you to confirm the short project code that goes into contract ids.

3 Ask for a piece of work

One sentence per task. The contract gets written for you, and then held against you.

You say Start a contract to add rate limiting to the payments endpoint
More than one at a time

For several pieces of work at once: "split this spec" gives you one contract per person with non-overlapping file areas, and "run the fleet" starts the ones that are ready — each in its own copy of the repository, from one recorded starting point. Nothing in a wave merges on its own; a single failure holds the whole wave's integration, including the parts that worked.

That runs /trellis:contract: it reads enough of the repo to write a contract that stands alone, declares which paths it may touch and how "done" gets checked as runnable commands, validates it, then asks you one question before creating the branch — wait for you at hand-over, or carry this through to merge. Then it branches, which is the step that arms the guardrails.

4 Know when it is guarding you

Trellis is deliberately silent outside the situation it was built for. Two conditions arm it, and both must hold.

5 What it will stop

Only while a contract is in flight. Each refusal explains itself and cites its rule.

AttemptResult
Edit a file outside writesDenied — scope is never widened mid-flight
Edit the contract being executedDenied — a wrong contract is fixed by a human, in a separate commit
git rebase, branch switch, merging by handDenied always under a contract
git push, gh pr createDenied on a supervised contract. Allowed on one you granted autonomy, if the base branch has required checks
Push to main or force-pushDenied always, contract or not
Finish with a red buildThe session may close — but the contract is marked blocked and you are told
Not a sandbox

Defence in depth against drift, not a security boundary. A determined shell can evade a pattern, by design — the goal is that nobody wanders out of scope by accident.

· Who checks the work

The question a domain expert asks first, and the honest answer: what protects you is not your review — it is everything that runs before you ever see it.

WhenWhat happensWho
While the work happensAnything outside the agreed scope is refused, not negotiated. Pushing, merging and deploying are refused outrightNobody — mechanical
Before the session closesBuild, lint and tests are re-run from scratch. Not read off a summary — actually executed. A failure marks the work blocked and says soNobody — mechanical
Before a pull requestA second agent reviews the result with instructions to refute it, and never sees the first one's report. Only the files count as evidenceAn independent reviewer
Before anything mergesSomebody presses the button. AlwaysYou, or whoever owns the repo
Whenever you likeLook at the running product and say "that works, but functionally it is wrong"You
Why your review does not block

Deliberately. A review that blocks stops the work when the reviewer is travelling, and catches nothing a machine could not have caught earlier and cheaper. Yours is the one that catches what no machine can — that the thing built is not the thing wanted — and that is easiest to see on the running product, not in a diff.

Say it whenever you see it. It becomes a change, not a rejection.

6 Reference

Doing it by hand instead

Everything the skills do is plain files and commands. Nothing is hidden.

With no git there is no branch to name the contract, so point at it explicitly — echo "MY-T-01" > .trellis/active. The hooks read that file exactly as they would read a branch name. Delete it when the contract is done. 

TRELLIS=$(echo ~/.claude/plugins/cache/gmstek/trellis/*/)

mkdir -p .trellis docs/specs docs/contracts docs/adr
cp $TRELLIS/templates/project-profile.yml .trellis/profile.yml
# fill in build / test_fast / lint · `~` means "none here", stated not blank

cp $TRELLIS/templates/CONTRACT.md docs/contracts/MY-T-01.md
node $TRELLIS/scripts/validate-contract.mjs docs/contracts --all
git checkout -b task/MY-T-01-short-slug
Keeping it current, and releasing changes 
claude plugin update trellis@gmstek

If you maintain the plugin: the install cache is keyed by version. New commits without a version bump in plugin.json reach nobody, and update will report already at the latest version. Bump it, then claude plugin tag --push.

What this costs in context

The four hooks are harness-only — no model context cost. The two skills cost about 240 tokens always-on (their descriptions, so the agent knows they exist) and roughly 1.9k when one actually fires. Check yours with claude plugin details trellis@gmstek.

That asymmetry is the whole argument for pushing rules down into hooks rather than writing them into documents: a hook is unforgettable and free.
